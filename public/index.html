Proof, not promises

What "world-class" actually looked like on our last build

Kington Parishes — a proof-of-concept rebuild for a five-church benefice — is where most of what follows was worked out for real, in public, with a git history you can read.

The brief, as it actually arrived, was a single line: “the top and bottom of the site look rather grey.” What followed wasn't a redesign brainstorm — it was a diagnosis. The header, hero and footer all shared one flat colour, repeated on every page, with nothing to break it up. The fix became a two-layer gradient technique — a dark, warm base every word of text sits on, and a bright glow confined to one corner, kept away from anything readable. You're looking at the same technique right now, on this page's own hero.

Accessibility wasn't a checkbox

Every colour pairing in that gradient was checked by relative-luminance calculation, not eyeballed — the palette was chosen specifically so the weakest text colour cleared 4.5:1 with real margin, not a bare pass. When a plain colour swap would have dropped a footer's fine print below that threshold, the fix shipped in the same commit, not as a follow-up ticket.

A hand-drawn sketch became a working feature

The site had a lovely pen-and-ink drawing of all five churches, sitting there decoratively, doing nothing. It's now a working navigation element — five invisible, precisely-measured hotspots overlaid on a responsive image, each one jumping to the right church, each one with a real accessible name for a screen reader, each one verified by hovering every single segment and checking it lined up with the actual building before it shipped.

Our engineering bedrock

Forty years of hard-won rules. Now with sharper teeth.

Before there was an AI workflow, there was Mr Wright's Rules — eight engineering principles honed over four decades of professional software practice. We don't treat them as a plaque on the wall. They're the actual mechanism that keeps AI-assisted work trustworthy.

  • 06

    Always test first

    With AI writing the implementation, the test suite becomes the real interface you're programming against — the thing you actually trust, whatever's underneath it.

  • 08

    Aim for 100% business-rule coverage

    A green build with full coverage buys the confidence to let an AI refactor, or even rewrite, a whole section — and trust it still works.

  • 05

    You own it, even if you didn't type it

    “The AI wrote it” is never a valid excuse. Every line that ships stands behind our name, reviewed by a person who understands it.

How we actually work

The AI writes code. It doesn't make decisions.

This is the part most agencies won't show you. Ours is deliberately boring — boring is the point.

1

Spec

Intent is written down before anything is built — what it should do, and just as importantly, what it shouldn't.

2

Tests

Written first, against the spec — the pass/fail bar the AI's output has to clear, not a formality added afterwards.

3

AI build

The AI implements against that bar — fast, but never the thing being trusted blindly.

4

Human review

A senior engineer reads every change. Confident-looking code isn't the same as correct code — we don't skim.

5

Ship

Tagged, logged, and live — with a changelog entry and a build number, every time.
